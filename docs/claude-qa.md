# Claude Q&A isolation prototype

This is a reviewable Linux prototype, **not an enabled Q&A provider**. Nothing registers it with Office, grants the Office service root access, installs a service, or changes a custodian's Claude configuration. Kimi/Codex capability decisions remain in their existing dispatch modules. The prototype needs independent privileged-boundary review, integration of its authenticated policy fetcher, selected-account authorization, and a real subscription acceptance check before integration.

The next integration step is a narrowly scoped root controller with fixed reviewed image/route/limits, app-side authorization, and root-side selected-custodian credential resolution. Native workers share the Office service UID, so a Unix socket UID check or sudo allowlist alone cannot authorize that controller. Admission must use the kernel-reported `SO_PEERCRED` PID and match the running Office service's current `MainPID`; caller-supplied PIDs and process ancestry are insufficient. This IPC and its independent review are deliberately not implemented here.

`src/server/claude-qa/runtime.ts` accepts one trusted, approved question, a selected access token, and fresh policy evidence. It launches only the pinned Claude Code **2.1.331** Linux x86-64 binary (SHA-256 `4c00839cf46beb2b38ec310105f2d538f7f9321fe46c636299b74bcab94626b1`) through the fixed C launcher. Callers cannot supply native arguments, executable paths, extra mounts, environments, models, or network destinations. The image path is an administrator-reviewed controller setting, never a user parameter. Do not expose this exported function directly through an HTTP request or general sudo helper.

## Boundary and data flow

The image contains the pinned native binary, a small loopback-to-Unix bridge, its glibc loader/libraries, and minimal static account/host files. It has no shell, package manager, project, host home, Claude credentials, refresh token, service socket, or Docker access. Image files and ancestry must be root-owned, protected from other writers, canonical, and match the file inventory and checksums. The manifest is root-trusted; it is not a signature protecting against a compromised administrator.

Each invocation gets a separate transient systemd unit, DynamicUser, private network namespace, readonly root, private `/work` and `/tmp` tmpfs, restricted execution paths, empty capabilities, and bounded CPU, memory, tasks and runtime. Only that job's Unix broker socket, local policy defense, job-specific CA certificate, and generated access-only native identity seeds are mounted. `/proc` hides other users' processes. The native process discovers a random one-job surrogate in its fresh credentials file, with the selected account/organization and subscription metadata; no refresh token is copied. An environment token alone can make native policy loading ineligible. The real selected access token stays in the trusted broker. The question arrives on stdin. Neither token nor prompt is placed in logs or native argv.

The fixed loopback bridge carries an HTTPS proxy CONNECT to only `api.anthropic.com:443`; the broker terminates job-specific TLS, and native trusts only that added CA without disabling certificate verification. No custom API base URL is set. The broker replays the two authenticated native policy GETs, then accepts one authenticated `POST /v1/messages` (optional `?beta=true`) and sends it only to Anthropic's fixed Messages endpoint. It preserves the native OAuth beta/version headers and substitutes the selected token. It requires the pinned model, `tools: []`, one approved question, text-only context, and at most 4,096 output tokens. Unknown body keys, alternate routes, second requests, tool blocks, malformed SSE, oversized output and redirects fail closed. Validated values are serialized before forwarding to prevent duplicate JSON keys from creating different interpretations. Responses are buffered and validated before the native process receives them; streaming UI is deliberately outside this prototype.

The runner stops its exact transient unit on completion/error. `KillMode=control-group`, `RuntimeMaxSec`, task/memory/CPU limits and a controller deadline contain native descendants. The job broker, policy file and host scratch directory are removed afterward. There is no broad process-name cleanup. The controller retains only a sanitized outcome, policy digest and forward/accept/deny counts. Kernel/systemd/native vulnerabilities are outside this process boundary's guarantee.

## Required managed policy

Policy is **not inferred from missing network responses**. `native-policy-adapter.ts` performs only bounded GETs to Anthropic's fixed `settings` and `policy_limits` endpoints with the selected existing OAuth access token. It never refreshes credentials, falls back to an API key, follows redirects, or substitutes an empty response. Both responses must be 200 JSON with a request ID and signed document. The adapter verifies ES256/P-256 signatures, the two-certificate chain against Claude 2.1.331's embedded public root, issuer and SAN marker, canonical body digest, lifetime, account and organization. A workspace claim is bound only when the canonical account supplies that identity; HTTP workspace headers are not an identity source.

The trusted evidence retains the original settings envelope/checksum, settings and limits documents, signatures, native identity and a fetch time no more than 60 seconds old. Production accepts only team/enterprise metadata with inference scope and sufficient remaining access-token lifetime. No other account's metadata may be used to change eligibility. The controller seam stays unavailable until independently reviewed and explicitly integrated; arbitrary app-supplied evidence is never trusted.

Supported settings contain only optional boolean `channelsEnabled`. Supported limits contain the five known boolean restrictions `allow_connector_file_downloads`, `allow_connector_file_uploads`, `allow_computer_use`, `enforce_web_search_mcp_isolation`, and `require_trusted_devices`; empty compliance taints; absent/null monitoring notice; and absent/false `remote_control_at_startup`. Unknown keys, nonempty compliance regimes, a required notice, and unsupported startup defaults fail closed. A restriction's `allowed:true` can mean an enforcement requirement: `require_trusted_devices:true` is preserved and governs Remote Control. The runner offers no Remote Control, connector, computer, or external action capability. It does not flatten those keys into ordinary permissions.

Native receives the full original remote policy through its genuine-host GETs. The local `disableAllHooks:true` file is defense in depth only; remote precedence may shadow it. OS containment remains necessary. Before exposing the real token to inference, the broker requires delivery of both policies, both exact pinned-native apply messages, and exact native-written document digests. The observer resolves only the generated unit's MainPID, checks its cgroup/start time, opens its kernel namespace root, and holds no-follow work/home/file descriptors. It reads only bounded policy/log files inside that unit's 32MB tmpfs. It adds no writable host-home mount and fails closed on missing files, links, changed documents or missing application evidence. Native alone may continue after a failed fetch; broker readiness prevents that from reaching the provider.

The smaller signed-cache-only path was not qualified: a scratch native run with unavailable policy endpoints reached its dummy inference request without affirmative policy-application evidence. No production cache fallback is implemented.

## Reproduce the dummy qualification

Use an administrator-controlled Linux x86-64 host with systemd 255, Node, Python and `cc`. Build the fixture bundles in the reviewed checkout; no credentials are needed:

```sh
mkdir -p /tmp/claude-qa-payload
node_modules/.bin/esbuild tests/fixtures/claude-qa-linux-driver.ts --bundle --platform=node --format=esm --banner:js="import { createRequire } from 'node:module'; const require = createRequire(import.meta.url);" --outfile=/tmp/claude-qa-payload/claude-qa-linux-driver.mjs
node_modules/.bin/esbuild tests/fixtures/claude-qa-boundary-driver.ts --bundle --platform=node --format=esm --banner:js="import { createRequire } from 'node:module'; const require = createRequire(import.meta.url);" --outfile=/tmp/claude-qa-payload/claude-qa-boundary-driver.mjs
node_modules/.bin/esbuild tests/fixtures/claude-qa-image-driver.ts --bundle --platform=node --format=esm --banner:js="import { createRequire } from 'node:module'; const require = createRequire(import.meta.url);" --outfile=/tmp/claude-qa-payload/claude-qa-image-driver.mjs
cp deploy/claude-qa/{launcher.c,build-image.py,qualify-linux.py} tests/fixtures/claude-qa-boundary.c /tmp/claude-qa-payload/
```

Transfer that reviewed payload to a root-owned private directory on the test host. As root, run `python3 PAYLOAD/qualify-linux.py EXACT_CLAUDE_BINARY PAYLOAD`. It creates a unique `/root/office-claude-qa-qualification-*` directory, builds with umask 077, and runs only in-process dummy transports. It never requests an actual provider response or reads a real credential. It leaves the image, sanitized JSON evidence and fixture image for review; no service is installed. Preserve `summary.json` before removing that exact generated scratch directory. The fixture image contains an extra probe and is intentionally rejected by production image verification.

The harness checks actual native startup and text answer, OAuth header shape with dummy substitution, `tools: []`, output bound, forged-tool/oversized response refusal, timeout, image tampering/writable files/symlinks/extra files, distinct job UIDs and scratch, hidden other-process state, readonly root, no host or external network, absent shell, hostile managed startup-hook containment, unreadable policy refusal, and cgroup descendant cleanup. The hostile hook's inability to modify a host canary is containment evidence; it does not prove every possible native hook behavior. No raw native transcripts or credentials are saved.

Focused repository verification: `node --import tsx --test tests/claude-qa.test.ts tests/claude-qa-policy.test.ts tests/size.test.ts` and `npm run typecheck`. The lead runs the repository's complete tests/build on the integrated candidate. Dummy runtime fixtures use opaque test policy signatures supplied by the trusted test controller; they never pass the production signature adapter. Separate signature tests generate their own test CA and verify that the production root rejects it. A protected recorded-policy check can test the production adapter against previously fetched, signed own-account metadata without a provider call. Dummy qualification does not establish real subscription inference, billing, account consent, or production readiness.
