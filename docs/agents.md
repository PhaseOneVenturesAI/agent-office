# Choosing an agent

Back to the [README](../README.md).

Every new worker starts on the office's **Default worker**: a provider, model and effort an admin picks in ⚙️ Settings → **🤖 Workers** (the `--agent` with its own default model until someone does). The hire, ask, queue, issue and meeting windows show it on one line; click **✏️ Edit** there to pick **Claude Code**, **Kimi**, **OpenCode**, **Codex**, **Grok**, **Muse**, **DeepSeek Harness**, **Pi** or **Cursor**, a model and an effort for just that worker or task, and **↺ Use the default** to go back. Board agents and tasks the Queue agent adds, which nobody picks for, start on the default too. Existing workers keep their provider when prompted or resumed, and queued tasks keep their choice when retried or restored after a restart.

## Personal credentials and ownership

Named Office accounts, including admins, use only their own Claude, Kimi or Codex sign-in from **☰ → 🔐 Your sign-ins**. The default provider is a model choice, not a credential owner. Missing personal credentials block hiring and resume; a saved **Use office credentials** choice and its old cached identity cannot authorize a launch. Other providers are refused for personal agents until Office supports their personal sign-ins. Shared-password host mode remains available separately.

New personal agent and shell processes use the account's existing `claude`, `kimi`, `codex` and `gh` homes under `.agent-office/homes/<account>/`, plus a personal `HOME` and XDG directories. Host provider keys, credential-file overrides, shell startup overrides and agent CLI arguments are not inherited. Agent model/effort selections still apply. Existing own native credentials and session IDs are retained; this change does not sign users out or replace their sessions. Shared and personal harness files continue to be applied to those same provider homes; harness choice does not change credential ownership. Personal task labels are generated locally instead of making a hidden host-Claude request.

Generated personal Git configuration no longer includes the host's Git config. On first use, an older generated host include is removed while retaining its personal identity and GitHub helper; the complete prior file is kept beside it as `gitconfig.before-personal-<unique-id>`. Keep that backup restricted: an old config can contain credentials.

Only the account that hired an agent can prompt, resume or control it, view its private terminal/Conversation, or reuse it through a board station, queue, meeting, review or Office worker tool. An admin role does not grant control of another account's agent or an Office-owned agent. A child hired through Office tools inherits its caller's owner. The small nameplate owner tag uses the verified account display name, never an editable character label or an email; it reads **Office** for ownerless workers, **Former account** for a removed account and **Unknown** for missing older-server data.

**First activation from a version that allowed host credentials:** perform a controlled shutdown and verify all old Office worker/terminal-host processes have exited before activating this version. Preserve worker records, provider session files and shell scrollback first. Adopting a running PTY cannot change the credentials already loaded in that process; an ordinary hot reload is insufficient for this transition. This is credential routing and Office control authorization, not OS isolation: native workers still run under the service user and can execute tools allowed by their provider.

## Models and effort

Every harness takes both a **Model** and an **Effort**, each optional: leave one on **Default** and the harness uses its own settings.

| Harness | Model | Effort |
| --- | --- | --- |
| Claude Code | Fable 5.1, Opus 5.5, Sonnet 5.5 or Haiku 4.5 (`--model`) | `--effort` |
| Kimi | a model id from its catalog, typed (for example `kimi-code/kimi-for-coding`) | **Thinking** (its `thinking` option) |
| OpenCode | a `provider/model`, typed or picked from the suggestions `opencode models` gives (`--model`) | the model's variant |
| Codex | one of the models `codex debug models` lists (`--model`) | `-c model_reasoning_effort` |
| Grok | one of the models `grok models` lists (`--model`) | `--effort` |
| Muse | a model id, typed (`--model`) | `--reasoning-effort` |
| DeepSeek Harness | a model id from its catalog, typed | its `reasoning_effort` option |
| Pi | a model name or `provider/model`, typed (`--model`) | **Thinking** (`--thinking`) |

The efforts are low, medium, high, extra high and max. Where a harness's own catalog says which of them a model supports (Codex and OpenCode do), the ones it doesn't are greyed out once that model is picked. A harness whose models can't be listed (its CLI isn't installed, or isn't signed in) still takes a model id typed in. A **Custom** `--agent` is run as it is, so it has neither field: set its model and effort in `--agent-args`.

What's picked shows next to the worker everywhere it's named (the Workers panel, its task card, its terminal's title, the queue), by the model's name rather than its family: **Opus 5.5**, not "Opus". For Claude Code that name comes from the session itself once the worker has spoken, so a worker left on Default says which model the default is, and one switched with `/model` in its terminal says the new one.

For OpenCode, the **Model** field selects the initial model for a new worker or queue task. Suggestions come from `opencode models`; you can also enter a `provider/model` ID. Leave it empty to use your OpenCode settings (including configured CLI arguments). An explicit choice overrides configured model arguments for that launch and stays with a queued task when retried. **Effort** is what OpenCode calls the model's *variant*. Its TUI has no flag for one, and sends each message at the variant it remembers for the model from whichever session used it last, so the office's plugin puts the worker's first message on the effort picked for it; the TUI carries on from that message, and `Ctrl+T` in the terminal still changes it. An effort the model has no variant for changes nothing.

**Pi** is available in the worker picker, queued tasks, meetings, and the office default. Install and sign in to the Pi coding-agent CLI on the machine running the office (`npm install -g @earendil-works/pi-coding-agent`, then `pi` and `/login`). The integration targets Pi 0.87.1 or later, using its `agent_settled` and UI prompt extension events. Choose Pi when hiring, or start the office with `--agent pi`. Windows npm `.cmd` launchers are supported.

Pi keeps its own login, settings, packages, and extensions. The office adds a CLI-loaded extension to report session, working, tool, waiting-for-input, and completion events; it does not edit your Pi configuration. Each worker's sessions live under `.agent-office/pi-sessions/<worker-id>`, and **R** resumes that worker's session. The optional **Model** field accepts a model name or `provider/model`; **Thinking** offers low, medium, high, xhigh, and max. Leave either on Default to use Pi settings or configured `--agent-args` (including `--thinking off` or `minimal`). Cost and token metrics remain in Pi's terminal and are not included in the office's Claude budget.

For Claude Code, the **Model** and **Effort** fields pick `--model` (`fable`, `opus`, `sonnet` or `haiku`, listed by the model each alias stands for: Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 4.5) and `--effort` (low, medium, high, extra high or max) for that worker or queue task, overriding whatever `--agent-args` set office-wide. Leave either on **Default** to use the office's configured value. The choice stays with a worker across resumes and with a queued task when retried, and shows up next to the worker in the Workers panel and on its task card so you can tell at a glance who's on what — and the per-worker cost there reflects the actual model used.

Kimi has no interactive terminal, so the office drives it over **ACP** (`kimi acp`, newline-delimited JSON-RPC on stdio), exactly the way it drives DeepSeek Harness: the laptop shows the transcript the office renders — committed messages, thoughts, tool calls and their outcomes, approvals with the same keys (**Enter** allows once, **Esc** rejects, a number picks), and what is in the context window. Type a line and press **Enter** to send it as one prompt; **Esc** or **Ctrl+C** cancels the turn. The **Model** field names a model from its catalog (typed, for example `kimi-code/kimi-for-coding` or `kimi-code/k3.1-pro`), applied with `session/set_config_option`, and **Thinking** maps onto Kimi's own ladder (`low`, `high`, `max`): the office's *Medium* and *High* land on `high`, *Extra high* and *Max* on `max`. Leave either empty for the account's default. **R** resumes the worker's session. A Kimi worker runs on the sign-in of whoever hired it (🔐 Your sign-ins): their own `KIMI_CODE_HOME` under `.agent-office/homes/<account>/kimi` from a device login, or a pasted `KIMI_API_KEY`. Its ACP session is a child of the office process, so like a DeepSeek Harness worker it stops with the office and comes back *offline*, resumable with **R**.

In an open OpenCode terminal, **Models** opens the native model picker using the default `Ctrl+X M` shortcut. Select a model there to change the active worker without restarting it or losing a draft. If you customized that binding, use your configured shortcut or `/models` inside the terminal. Resuming a saved session lets OpenCode restore its current model instead of forcing the initial Office selection again.

Claude Code remains the default. To default to OpenCode:

```bash
agent-office /path/to/project --agent opencode
```

`--agent-args` applies only to the provider configured by `--agent`; choosing another provider uses its normal command and settings. OpenCode model flags therefore never reach Claude Code, and vice versa. Grok's `--model` / `--effort` and Muse's `--model` / `--reasoning-effort` for a worker likewise stay with that provider. An arbitrary `--agent` executable remains available as **Custom**, with whatever model and effort its `--agent-args` give it.

OpenCode receives prompts through `--prompt` and resumes its saved session through `--session`. The office adds a local event plugin through `OPENCODE_CONFIG_CONTENT`, preserving existing inline JSON settings and plugin entries. Inline settings must be a JSON object; configuration files continue to use OpenCode's own loader. The office does not edit your OpenCode configuration files or bypass permission prompts. The bridge reports worker status to a loopback endpoint authenticated by a per-worker token. Kimi, OpenCode, Codex, Grok, Muse, DeepSeek Harness, Pi and the Cursor CLI must be installed separately on servers set up with `deploy/provision.sh` (or the AWS script), which installs Claude Code only.

Grok uses its interactive CLI with `--no-alt-screen`, a per-office `GROK_HOME` for session and hook files (your grok.com login is still read from `~/.grok/auth.json`; 🔐 Your sign-ins is Claude, Kimi, Codex and GitHub), and resumes through `grok --resume <session-id>`. Set it as the default with `--agent grok`. The office writes command hooks into that isolated home so a worker can report status without editing `~/.grok/hooks`. `--trust` skips Grok's folder-trust prompt for the project the desk is already in; native permission prompts still appear in the terminal. The **Model** and **Effort** fields pick `--model` and `--effort` for that worker or queue task. Leave either on **Default** to use your Grok settings. Token spend stays in the worker terminal; the office does not meter grok.com billing.

Muse uses its interactive CLI with `--trust-workspace`, a per-office XDG tree under the floor's `.agent-office/muse-home` (your login is linked from `~/.config/muse/auth.json`; 🔐 Your sign-ins is Claude, Kimi, Codex and GitHub), and resumes through `muse resume <session-id>`. Set it as the default with `--agent muse`. The office writes command hooks into that isolated home so a worker can report status without editing `~/.config/muse`. `--trust-workspace` skips Muse's folder-trust prompt for the project the desk is already in; native permission prompts still appear in the terminal. The **Model** and **Effort** fields pick `--model` and `--reasoning-effort` for that worker or queue task. Leave either blank / on **Default** to use your Muse settings. A follow-up prompt on resume is pasted into the TUI after SessionStart, because `muse resume` does not take a prompt on argv. Token spend stays in the worker terminal; the office does not meter Muse billing.

DeepSeek Harness has no interactive terminal, so the office drives it over its **ACP profile** (`dsh --profile acp`, newline-delimited JSON-RPC on stdio) instead of a PTY. The laptop still shows a terminal, but it is the transcript the office renders from ACP: committed messages, thoughts, tool calls and their outcomes, and what is in the context window. Type a line and press **Enter** to send it as one prompt; **Esc** or **Ctrl+C** cancels the turn. There are no slash-commands (`/compact` and friends are not on the ACP surface), and the terminal does not resize the agent. Status comes from the ACP session itself: `session/prompt` in flight is *working*, an outstanding `session/request_permission` is *needs input*, and a settled turn is *done*, with no hooks to install or trust.

The **Model** field names a model from its catalog: type the model id (`deepseek-v4-pro`) and the office matches it against the options the session advertises, then applies it with `session/set_config_option`. The **Effort** field works the same way, on DSH's own ladder (`low`, `high`, `max`): the office's *Medium* and *High* both land on `high`, and *Extra high* and *Max* on `max`. Leave either empty for the profile's default. A saved choice the harness no longer offers is reported in the terminal and the profile default is used instead.

The transcript is styled after the harness's own chat, in its colors (its `--dsw-alias-*` dark-theme tokens) and its wording:

- **Reasoning** opens a `✻ Think` block, ruled down the left in the harness's tertiary text color, and closes with a blank line before the answer. It is never italic, matching the chat.
- **Markdown is rendered**, not printed raw: headings, bold, italic, inline code (on the harness's code background), bullets, quotes, links and fenced code blocks all come out formatted.
- **A tool call is one row**: its icon, the harness's own title for that tool (`Bash`, `Read`, `Search`, `Edit`, `Write`, `Code`, `Fetch`…), a dot, and the argument it summarizes by (the command, the path, the query), in the chat's secondary/tertiary colors. A finished call is left collapsed the way the chat leaves it, so there is no tick and no second line; a call that **failed** gets a `└` line in the error color with the reason and up to eight lines of its output.
- **Each turn ends with the chat's process row**: `Worked · 3 tool calls`, or `Stopped` when you cancelled, or `Failed`.
- **An approval** is the harness's approval card in text: `▲ Waiting for approval` plus `Tool <name> requests privileged execution`, the numbered choices (reject in the error color, allow in the warning's), and the same keys the chat binds: **Enter** allows once, **Esc** rejects, or a number picks any listed choice. Enter only ever means *allow once*: a request that offers only *always* needs its number typed, and a blank line in something you paste is not an Enter. The card shows the full command being approved. The turn genuinely blocks until it is answered, and rejecting does not end the turn.

Anything the harness sends that this surface has no place for (plans, modes, commands) is skipped rather than printed, and escape sequences in model or tool text are stripped so nothing it says can redraw the terminal.

Set it as the default with `--agent dsh`, and choose the profile with `--dsh-profile <name>` (default `acp`, also `AGENT_OFFICE_DSH_PROFILE`). `--agent-args` is passed through ahead of the profile flags when DSH is the configured agent. DSH rewrites its own profile file on every boot, so the user running the office needs write access to `$DSH_HOME` (`~/.dsh`); a read-only home fails the launch before any ACP frame is exchanged. The office writes a per-floor patch (`<project>/.agent-office/dsh-patch.yml`) that points DSH's session persistence at `<project>/.agent-office/dsh-sessions`, so **R** resumes exactly the session that worker started instead of whatever is in your `~/.dsh`. A new hire always starts a session of its own; it never picks up another desk's. Resuming a session restores its log without replaying the old turns. Its ACP session is a child of the office process, so unlike the other providers a DeepSeek Harness worker stops with the office and comes back *offline*, resumable with **R**. Driven over ACP as verified against `dsh 0.1.7-rc.2`; see [dsh-acp-integration.md](dsh-acp-integration.md) for the design.

Cursor runs the Cursor CLI's terminal (`cursor-agent`) on the office machine's own Cursor login: `cursor-agent login`, or `CURSOR_API_KEY` in the office's environment (🔐 Your sign-ins is Claude, Kimi, Codex and GitHub; a Cursor worker hired by an account still gets that account's GitHub sign-in for `gh`). Pick **Cursor** when hiring, or set it as the default with `--agent cursor-agent`. A new worker starts with `--trust`, which skips Cursor's folder-trust prompt for the folder the desk is already in, with `--model` when one was picked, and with its prompt. **R** resumes its chat with `cursor-agent --resume=<chat id>` (the id its first hook names), and a follow-up prompt goes on that command line too. The office never passes `--force` or `--yolo`, and drops them from `--agent-args`: Cursor's own permission prompts appear in the terminal. The office-owned worktree is the worker's folder, so Cursor's own `--worktree` is never used.

The Cursor CLI reads hooks from `~/.cursor/hooks.json` and from `.cursor/hooks.json` in the folder it runs in, and nothing moves either, so the office never touches `~/.cursor` and puts each worker's hook entries in `.cursor/hooks.json` of the worker's own folder (its worktree, or the project itself for a board agent) as it starts. They come out when the worker's process ends, when it's sent home and when the office stops, and the file goes with them when it held nothing else. A file the office made is listed in `.git/info/exclude`, so it never counts as a change of the worker's. A project with a `.cursor/hooks.json` of its own keeps its hooks: the office's entries go in next to them, and the file is put back as it was afterwards, though git shows it as modified while a Cursor worker runs there. One with comments in it is left alone, and a worker there reports no status.

The entries (`sessionStart`, `beforeSubmitPrompt`, `preToolUse`, `postToolUse`, `postToolUseFailure` and `stop`) report to a loopback endpoint with a per-worker token, and pass on only the chat id, your prompt and the tool's name: never the assistant's messages, tool input or output. A subagent's events are ignored. They answer Cursor with no decision of their own. Cursor has no hook for a permission prompt, so a worker waiting on one shows as *working*, with the tool it wants to run, until you answer it in its terminal. A worker on a machine where Cursor isn't signed in is flagged as needing you, and its terminal is where you log in. The **Model** field takes a Cursor model id, with suggestions from `cursor-agent models` when the CLI is signed in; leave it empty to use your Cursor settings. Cursor has no separate effort flag: a parameterized model takes it in brackets, as in `claude-opus-4-8[effort=high]`. Usage and cost stay in Cursor's terminal and your Cursor account; the office doesn't meter them, and the daily budget stays Claude-only. Written against Cursor CLI 2026.09.08.

Codex uses its interactive CLI with `--no-alt-screen`, runs on the sign-in of whoever hired it (🔐 Your sign-ins): a device login or pasted OpenAI API key lives in the account's own `CODEX_HOME` under `.agent-office/homes/<account>/codex`, admins may use the office machine's own, and an office without accounts keeps the machine's login as before. preserves native sandbox and approval settings, and resumes through `codex resume <session-id>`. Set it as the default with `--agent codex`. The **Model** field lists the models Codex's own picker shows (from `codex debug models`) and **Effort** the levels the picked model supports; they go on its command line as `--model` and `-c model_reasoning_effort=…`, when it's resumed too (Codex resumes on its current settings, not the session's), and a worker's own model replaces a `--model` in `--agent-args`. Leave either on **Default** to use your Codex settings; `/model` inside its terminal still changes both. The office supplies command hooks through per-process config overrides, without editing your Codex configuration. On first use, open the terminal, complete any login/setup, and review the generated Office commands in `/hooks`. Hooks need your native trust approval before session/status tracking works; the office never bypasses that review. Workers that do not report startup are marked as needing input. Codex tasks use local summaries and do not launch Claude for task naming. Its token metrics come from the root rollout identified by the trusted hook, under `CODEX_HOME/sessions` or `CODEX_HOME/archived_sessions` (default `~/.codex`). The reader checks the session identity, bounds file reads, and sends only normalized counters to the browser. Snapshots update after hooks and on a 10-second poll, survive restarts, and reset for a new session. Cache and reasoning are counted once. Child-session usage is excluded; USD cost and API-call counts are shown as unavailable. The rollout format is version-dependent (verified against 0.154.0); missing or unsupported records remain unavailable instead of being shown as zero. Reads inspect at most a 1 MiB header and the latest 4 MiB of a rollout; if no newer counter is found in that tail, the last known snapshot remains visible.

OpenCode metrics come from assistant-message token/cost records exposed by its plugin SDK. Updated messages replace prior values so streaming updates do not add the same call twice; existing root and child sessions are loaded on resume. History that is still loading or unavailable is labeled as partial. These snapshots update usage only, so a report cannot dismiss a permission request. The daily budget and historical ledger remain Claude-only.

DeepSeek Harness metrics come from ACP `usage_update`: tokens in context and the window's size, shown per worker and for the current desks, plus a session cost only when the harness reports one. The daily budget and historical ledger remain Claude-only.

Kimi metrics come from the same ACP `usage_update`: tokens in context and the window's size per worker, plus a session cost only when Kimi reports one. The daily budget and historical ledger remain Claude-only.

## The office's prompts

Everything the office tells a worker by itself can be rewritten in ⚙️ Settings → **🤖 Workers** → **📝 Edit the prompts…**: what **🤖 Hand to a worker**, **🔍 Review**, **Fix up & merge**, **Fix conflicts & merge** and **✍️ Ask a worker** send from the boards, what a meeting about an issue or a review panel starts with, the note the queue adds to a worktree task, the three board agents' briefs, every part the meeting room hands out, and the instructions for the model that writes the signs over workers' heads. Each one lists its `{{placeholders}}` (the issue number, the PR's branch, the file a meeting waits for…), which the office fills in when it sends it, and warns when one the office counts on is missing. **↺ Default** puts the office's own wording back. Admins edit them; they're the same on every floor and kept in `.agent-office/prompts.json` with the Default worker.

## The shared harness

Beyond the office's own prompts, a team's standing instructions — `CLAUDE.md`, workflow and taste notes, and the `skills/` every worker should have — live in the harness root: `$AGENT_OFFICE_HARNESS`, else `~/Documents/AgentHarness`, else the office's data dir. Admins browse and edit those files from **☰ → 🧰 Harness** (every save keeps a `.bak`; writes are jailed to Markdown, text, JSON, TOML and YAML under the root, 256 KB each). **📣 Push to everyone's agents** copies them into the office's own and every account's agent homes: `CLAUDE.md` and `skills/` into each `claude` home, and the root's instruction files as one `AGENTS.md` (marked per source file, anything it replaced kept as `.bak`) plus `skills/` into each `kimi` and `codex` home — the files Kimi Code and Codex already read — so the next worker anyone hires starts on the same page, whichever CLI it runs on. Someone who'd rather run their own setup picks **🙋 Use my own harness** in ☰ → 🧰 Harness (or **Run my own instead** in 🔐 Your sign-ins); their home gets a `.no-harness` marker and pushes skip them until they switch back. In the same panel they keep their own `CLAUDE.md`, `WORKFLOW.md`, `AGENTS.md` and `skills/` in `.agent-office/homes/<account>/harness/`, start from a copy of the office's, and **📣 Apply to my agents** writes them into their own `claude`, `kimi` and `codex` homes only — Claude gets `CLAUDE.md` and `skills/`, Kimi and Codex get `AGENTS.md` (or `CLAUDE.md`) and `skills/`, each with `WORKFLOW.md` after. Nobody else can open them, and the office's push never touches them. See [Personal harness](features.md#personal-harness).

One block of the root's `CLAUDE.md` manages itself: the **review ratchet**. Every verdict from the 🎬 Review room (☰ menu) is appended there, newest first, capped at thirty — what reviewers accepted and rejected, with the reasons. It reaches every agent home on the next push, so a worker never repeats a rejected take. Write your own instructions above the block, never inside it.

## Conversation and explicit handoffs

The **Conversation** button in an existing worker’s terminal opens a text-and-voice view of that same session. It never hires, resumes, switches models, or changes the provider automatically. Claude and Codex use their authenticated Stop hooks to read only the selected root session’s bounded transcript tail under that worker’s provider home. Kimi uses structured ACP assistant text from the current session and emits a reply only after a successful completed turn. Unknown formats, thoughts, tools, subagents, terminal control sequences and recognizable credential patterns are excluded. The transcript parser is a compatibility surface, not a stable provider API: if the CLI changes its format, use the terminal until the adapter is updated.

The view contains up to 30 new messages (100,000 characters total) in server memory, starting from replies observed by this Office process. It is not a migrated chat archive; earlier history remains in the agent’s terminal/provider session. Restarting Office clears this view, and changing the underlying session clears its buffer. Only the worker’s credential owner on its floor may subscribe or send. Named accounts cannot use Office-owned workers. Other colleagues’ personal workers are not readable through this panel.

Dictation inserts into an editable draft. **Send** requires an idle or done worker, and never answers a pending approval or queues a second turn. **Speak new replies** is off initially and uses browser/OS speech synthesis, preferring a local voice when available. Old transcript messages are not automatically spoken. Code blocks, inline code and URLs are omitted from speech; known credential patterns suppress the whole assistant reply. This is not a guarantee that arbitrary sensitive prose can be detected: keep sensitive work in text. **Stop audio**, disconnecting, closing or switching panels stops speech/dictation. **Interrupt turn** is separate, is allowed only while working, and never selects a permission option; resolve requests in **Terminal / approvals**. Browser dictation availability and speech voices depend on the browser/OS.

**Handoff** records one current optional handoff alongside the worker’s saved state. It requires two existing agents on the current floor in distinct canonical physical worktrees, owned by the requesting account (or both ownerless in shared-password host mode). Include scope, accepted constraints, evidence or an explicit unverified note, and a concrete next step. The server snapshots both actual Git branches/workspaces and returns the exact prompt for review. **Acknowledge context and send once** rechecks both workspaces/branches and idle states; it refuses busy agents, questions/permissions, missing checkouts, changed branches, duplicate acknowledgments and failed receipt persistence. Cancel a pending preview to prepare a corrected one.

The acknowledgment is saved atomically before one-shot delivery. A crash at that boundary may leave delivery uncertain; inspect the recipient’s existing session before preparing a replacement. The receipt is never automatically replayed. A failed delivery remains marked failed; evidence is human-supplied, not automatically certified. Handoff does not stop the source agent, transfer provider credentials, move files, create workers, merge branches, bypass tools, grant deployment approval or alter existing release gates. Keep coordinating source work with the existing project lead.

In **Your sign-ins → Provider readiness**, an explicit check reuses the sign-in service’s current inspection (up to its existing cache interval) and resolves installed commands on this host. Kimi/Codex credential-file presence, pasted tokens and CLI-reported sign-ins are labelled by their evidence rather than treated as live service validation. Models show selected configuration separately from the last model reported by your floor’s workers. Subscription quota is unknown here; token/cost totals are not remaining allowance. No background login, provider fallback or model switching is introduced.

## ACP shutdown and restarts

SIGTERM keeps hosted PTY sessions running in their separate terminal host so the next Office process can adopt them. Kimi and DeepSeek ACP sessions are in-process children, so Office sends `session/close` and awaits each child’s observed exit before the parent exits. If a child stays alive, its exact child-process handle receives SIGTERM after 500 ms and SIGKILL after 1.5 seconds. If its exit is still unobserved at 2.5 seconds, shutdown reports failure and exits nonzero; inspect that child before retrying a release. There are no name-based or process-group kills. Repeated shutdown signals do not skip pending cleanup.

The existing worker/session metadata and worktrees are retained for restart/resume. Hosted PTY keep/detach behavior is unchanged. Sending an ACP worker home also awaits its child’s exit before workspace cleanup; its record and desk remain reserved during that wait, and a failed stop preserves both. Queue recycling waits for successful removal before seating the next worker. Worktree recovery cannot resume a replacement process before the old ACP child exits. ACP closes already in progress are included in Office shutdown.

Removing a floor leaves it registered until shutdown succeeds; failed shutdown leaves its floor and worker records in place and reports the error. Clearing a meeting keeps its current ownership until all seated workers stop. A failed stop leaves the meeting, notes and shared worktree available for inspection and retry; it does not free the table for a replacement meeting. Pending stop/recovery blocks new prompts, resume and handoffs for that worker.
